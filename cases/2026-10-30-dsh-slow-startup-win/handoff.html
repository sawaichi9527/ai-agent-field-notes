1. TL;DR

三句話

  1. 「dsh web 慢」有兩種截然不同的成因，先量 CPU 時間與實際耗時的比值就能分開；不要憑感覺查。
  2. 來源機是 CPU 密集：16 秒裡 13.3 秒是 CPU，比值 108–126%，代表行程全程在算、沒有在等。其中約 39% 是檔案 metadata 查詢（lstat/stat/realpath）、約 17% 是 V8 編譯 JS，DSH 自己的邏輯只佔 19.5%。
  3. 目標機剛升到 0.2.1-rc.5，最可能的原因是升級本身（peer-dep 重新檢查、外掛被 skip、node_modules 重鏈、殘留的失效 patch 條目），因此第 6 節的檢查優先於第 5 節的效能量測。
    已被目標機否證 目標機沒有 skip、沒有豁免、沒有失效 patch 條目，比值 106–109%——原因就是第 5 節那條路（CPU 密集的模組載入）。第 6 節請降級為「只在日誌真的出現 skip 時才查」。

目標機覆核後的四句話

  1. 判讀方法有效且可複製。目標機量到 CPU/wall 106–109%，落在 ≥90% 的「CPU 密集」→ 不要查磁碟、不要加防毒排除，這個處置在目標機上也正確。
  2. 但幅度不等於來源機。目標機 21.6 秒 vs 來源機 16.1 秒，差額由 CPU 世代解釋（2008 的 Core 2 Quad Q9500 vs 2013 的 i7-4900MQ）。23.3 秒 CPU 時間就是該機的地板，砍 bundle 只能把 21.6 拉回 ~16 秒。
  3. 本文件從未量「0.2.0 → 0.2.1 的差」。它量的是 rc.5 的絕對值，卻被拿去對比「體感」。若原始抱怨是「升級後變慢」，這一題仍然沒有答案（見 第 14 節）。
  4. 超過一半的「升級後優先檢查項」在目標機不適用。沒有 compatibility.json、沒有 did not activate 警告。先讀 第 12 節，不要照抄。

2. 你要完成的 3 件事

4. 判讀規則（先分類，再查原因）

啟動完成後，看「CPU 時間 ÷ 實際耗時」。這個比值不需要 CPU 剖面，卻足以決定接下來往哪查：

比值代表接下來查什麼
≥ 90% CPU 密集：模組載入／編譯／metadata 解析在吃時間 外掛與檔案數量（第 5 節）、CPU 世代。不要查網路與防毒。
50–90% 混合：有明顯的等待成分 先做 CPU 剖面找出等待點，再逐一對照外掛的啟動期 I/O。
< 50% 在等待：I/O、防毒過濾驅動、網路逾時 外掛設定裡的 baseURL、requestTimeoutMs、registry／市集抓取；Defender 即時掃描；磁碟。
為什麼這個指標可靠：它是「行程自己用掉多少 CPU」對「牆上時鐘」的比。若行程在等 kernel、等網路、等防毒回覆，CPU 時間會遠低於實際耗時；若全程在算，比值會接近 100% 甚至超過（V8 背景執行緒可讓它到 120% 以上）。

5. 量測步驟（可直接貼上）

5.1 先決定「誰來跑」

關鍵限制：從 DSH 的沙箱裡跑 dsh web 會失敗。每次啟動都會重寫 profile 的 cordis.yml，而 DSH 代理的檔案沙箱只允許寫 session workspace，於是會在 prepareProfile 階段直接丟 EPERM: operation not permitted, open '…\profiles\web\cordis.yml'，量不到真正的啟動時間。

兩個可行做法，優先選 (a)：
  • (a) 請使用者在自己的 PowerShell／cmd 視窗執行（就是平常跑 dsh web 的那個視窗）。最忠實，也避開沙箱。
  • (b) 代理自己跑：需要 danger-full-access 核准，且要接受它會改寫真實 profile 的 cordis.yml。（原文另擔心 patchReload: live 會觸發 live 重組——目標機覆核發現這個鍵在 rc.5 程式碼裡完全不存在，已是失效鍵，該風險不成立。）

目標機覆核補充：阻擋比上面寫的多三層。以下全部實測：

  • 連 --dump-config 也會死在同一個 prepareProfile：dump-config → prepareProfile → writeFileSync → EPERM。所以「只印設定、不改檔」這條路也不通。
  • 連「spawn 一個要擷取輸出的子行程」都被拒：& pwsh -File .\measure-dsh-web.ps1 → Program 'pwsh.exe' failed to run: 存取被拒。；ProcessStartInfo.RedirectStandardOutput 同樣走不通。
  • 因此 agent 內拿不到任何行程 CPU 時間：Get-Process、tasklist、Get-CimInstance、Get-NetTCPConnection 一律拒絕存取 → 附錄 B 的 TotalProcessorTime 這條路在 agent 內不可用。
  • New-Item -ItemType Junction → 存取被拒，所以第 9 節「鏡像 + junction」的做法在沙箱內也不可行。

→ 結論不變，但更強：量測只能由使用者在自己的一般視窗執行；代理能做的只有「唯讀取證」與「隔離鏡像」，而後者的比值不可信（見 第 13 節）。

5.2 量測腳本（在一般 PowerShell 視窗執行，不需管理員）

存成 measure-dsh-web.ps1 後執行 pwsh -File .\measure-dsh-web.ps1 -Runs 3。它用另一個 port 起暫存實例量到第一行網址出現為止，然後把該行程殺掉，不會影響原本 3080 上在跑的實例。

param(
  [int]$Runs = 3,
  [int]$Port = 3099,
  [string]$Profile = 'web'
)
$ErrorActionPreference = 'Stop'

$bin = Join-Path (npm root -g) '@deepseek-ai\dsh\lib\bin.js'
if (-not (Test-Path $bin)) { throw "找不到 dsh 的 bin.js：$bin" }
$node = (Get-Command node).Source
Write-Host "node   : $(& $node -v)"
Write-Host "dsh    : $(& $node $bin -V)"
Write-Host "bin    : $bin"
Write-Host "profile: $Profile"
Write-Host ''

$results = @()
for ($i = 1; $i -le $Runs; $i++) {
  $p = $Port + $i - 1
  $sw = [System.Diagnostics.Stopwatch]::StartNew()

  $psi = New-Object System.Diagnostics.ProcessStartInfo
  $psi.FileName = $node
  $psi.Arguments = '"{0}" "{1}" --port {2} --no-open' -f $bin, $Profile, $p
  $psi.RedirectStandardOutput = $true
  $psi.RedirectStandardError = $true
  $psi.UseShellExecute = $false
  $psi.WorkingDirectory = (Get-Location).Path
  $proc = [System.Diagnostics.Process]::Start($psi)

  $outTask = $proc.StandardOutput.ReadLineAsync()
  $errTask = $proc.StandardError.ReadLineAsync()
  $urlMs = -1
  $deadline = (Get-Date).AddSeconds(180)
  while (-not $proc.HasExited -and (Get-Date) -lt $deadline) {
    if ($outTask.IsCompleted) {
      $line = $outTask.Result
      if ($null -eq $line) { break }
      if ($urlMs -lt 0 -and $line -match '://127\.0\.0\.1:\d+') { $urlMs = $sw.ElapsedMilliseconds; break }
      $outTask = $proc.StandardOutput.ReadLineAsync()
    }
    Start-Sleep -Milliseconds 25
  }

  try { $proc.Refresh() } catch {}
  $cpuMs = if ($proc.HasExited) { -1 } else { [int]$proc.TotalProcessorTime.TotalMilliseconds }
  if (-not $proc.HasExited) { try { $proc.Kill($true) } catch {} }

  if ($urlMs -lt 0) { Write-Host ("run {0}: 逾時，沒有看到網址列" -f $i) }
  else {
    Write-Host ("run {0}: {1,7} ms  (CPU {2} ms, CPU/wall {3:P0})" -f $i, $urlMs, $cpuMs, ($cpuMs / [Math]::Max($urlMs,1)))
    $results += $urlMs
  }
}

if ($results.Count -gt 0) {
  $sorted = $results | Sort-Object
  $median = if ($sorted.Count % 2 -eq 1) { $sorted[($sorted.Count - 1) / 2] } else { ($sorted[$sorted.Count / 2 - 1] + $sorted[$sorted.Count / 2]) / 2 }
  Write-Host ''
  Write-Host ("=== 中位數 {0} ms（{1:N1} 秒）  min {2} / max {3} ===" -f $median, ($median / 1000), $sorted[0], $sorted[-1])
}

注意：這個腳本只用到公開旗標 --port、--no-open，不碰 DSH 內部 API，因此 rc.2 與 rc.5 都可直接使用。

6. 升級到 rc.5 後優先檢查項

目標機覆核：本節 6.1 與 6.2 在目標機不適用
目標機完全沒有 compatibility.json（整個 ~/.dsh 遞迴搜尋 0 筆），也沒有 did not activate 警告、cordis.patch.yml 裡也沒有 forge-tools 條目。這兩項是來源機的歷史狀態，不是通用檢查項——照著查只會浪費時間。
正確的順序是：先量 CPU/wall（第 5 節）；只有當日誌真的出現 skipping／did not activate 時才回來查本節。

目標機是升級後才出問題，這一節應該排在效能量測之前。依可能性排序：此排序已被目標機推翻

6.1 peer 相容性重新檢查 → 外掛被 skip 目標機不適用

來源機的歷史紀錄顯示：全域重裝成 0.2.0-rc.2 時，多個外掛因 peerDependencies 指向舊版而被拒絕載入，當時是靠在 profile 的 compatibility.json 寫「精確版本豁免」才救回來，而豁免的鍵是 名字@版本、值是精確的 DSH 版本（例如 ["0.2.0-rc.2"]）。

豁免綁的是精確版本。升到 0.2.1-rc.5 之後，原本寫 0.2.0-rc.2 的豁免很可能不再匹配 → 外掛被 skip 或改走別的路徑 → 啟動行為與載入的模組集合都會變。 
# 看目前有哪些豁免、是否還對得上現在的版本
dsh plugin --profile web version-exemptions
Get-Content "$env:USERPROFILE\.dsh\profiles\web\compatibility.json"
Get-Content "$env:USERPROFILE\.dsh\dsh-web.log" -Tail 60 | Select-String -Pattern 'skipping|skip|incompat|did not activate'

6.2 殘留的失效 patch 條目（「N entry did not activate」）目標機不適用

來源機每次啟動都印 dsh: warning: 1 entry did not activate，原因是 cordis.patch.yml 裡有一條指向 @maxhsu/dsh-forge 的 forge-tools 條目，而該套件在任何 node_modules 根目錄都不存在。這種條目不會讓啟動變慢（它立刻失敗），但會掩蓋真正的外掛問題，也會在升級後混淆判斷。

# 列出 patch 條目，逐一確認套件真的存在
Get-Content "$env:USERPROFILE\.dsh\profiles\web\cordis.patch.yml"
# 把每條的 name 拿去測：Test-Path "<node_modules 根>\<name>"

6.3 node_modules 是否被重鏈（檔案數量暴增）

升級若動到依賴，pnpm 會重寫 node_modules；檔案數變多，第 3.2 節那 39% 的 metadata 成本會等比例上升。把量到的檔案數跟附錄 A 比對，而不是憑印象。

6.4 Node 版本是否跟著換了

9. 安全注意（會誤刪真實檔案）

junction 陷阱

來源機用「鏡像 DSH_HOME + junction 指向真實 node_modules」的方式做隔離量測。若你也要這樣做，刪除時必須先個別移除 junction：

# 正確：只刪連結本身
cmd /c rmdir "<鏡像目錄>\node_modules"

# 危險：Remove-Item -Recurse 可能沿著 junction 走進去，
# 把真實的 node_modules 內容一起刪掉
Remove-Item "<鏡像目錄>" -Recurse -Force   # 先確認 junction 已全數移除再執行

來源機的做法是：先對每個 junction 執行 cmd /c rmdir，再確認真實路徑（…\.dsh\profiles\web\node_modules\dshmarket\package.json 等）仍然存在，最後才刪鏡像目錄。

  • 建立 junction 需要超出 workspace 的權限（來源機在 workspace-write 下被拒 存取被拒，需 danger-full-access）。
  • 不要在原實例還在跑、且 profile 設了 patchReload: live 時去改 cordis.patch.yml——可能觸發 live 重組。來源機改檔前先備份到 workspace，改完只做了靜態驗證（YAML 解析 + 套件存在性），沒有在原實例上跑第二次 boot 去驗證，就是為了避免干擾。
  • ~/.dsh 內有 .credentials.yaml；量測用的鏡像 DSH_HOME 不要順手複製憑證檔。來源機實測：缺憑證檔不影響量到「印出網址」的時間點。

13. 方法論陷阱：沙箱內量到的比值不可用新增

我踩過的坑（請不要重犯）

覆核過程中，我先在 agent 沙箱內用「workspace 鏡像 DSH_HOME + 只留 2 個官方 bundle」量測，得到 wall 37–48 秒、CPU/wall 55–70%，據此一度判斷「目標機是混合、有明顯等待成分，因此第 8 節排除磁碟／防毒的結論不成立」。

這個判斷是錯的。同一個真實對象在沙箱外只有 21.6 秒、108%。

兩個污染源同時作用：

  • 鏡像 profile 沒有 node_modules → 走「安裝範圍解析」路徑，做真實 profile 不會做的 I/O。
  • 子行程在 DSH 沙箱內 → 每個 open 多一層 ACL 檢查，wall 被拉長而 CPU 不漲，比值於是被系統性壓低。

規則：CPU/wall 這個比值只有在沙箱外量才有意義。沙箱內的能量（wall、比值）只能當「有跑起來」的證據，不能拿來分類。

若要取證（不是定論），可重用的繞過方式是：DSH_HOME 指向 workspace 內的鏡像、子行程 stdout 重導向到檔案（不要用管線）、子行程內用 NODE_OPTIONS=--import 預載量 process.cpuUsage()。這樣完全不必碰真實 profile，但結論仍須用沙箱外的量測確認。

14. 仍未回答的問題與後續新增

本文件量的是「絕對值」，不是「退化幅度」

第 3 節與第 11 節都只證明「rc.5 在這台機器上很慢、而且是 CPU 造成的」。但原始抱怨是「升級到 0.2.1 後比 0.2.0 慢很多」——這需要 v0.2.0 vs v0.2.1 的同機 A/B，本文件從頭到尾沒有做。

做法很明確：目標機的 npm cache 仍留有 dsh-0.2.0 的 tarball，可離線裝到獨立 prefix，兩個版本走同一個鏡像 DSH_HOME、用同一支腳本量。兩版污染因子相同，差值可信。這一步才會回答「0.2.1 是不是真的比較慢、慢多少」。

14.1 可操作的槓桿（依效果排序）

  1. 砍 bundle：10 條 → 2 條官方。換算基準：來源機 9 條 16.1 s、2 條 11.9 s，差 4.2 s／7 個第三方 ≈ 0.6 s／個。目標機 CPU 更弱，預期 −5~6 秒（≈25%）。
    注意 這是「回到 ~16 秒」，不是「回到 v0.2.0 的速度」——兩件事不要混為一談。
  2. 確認退化幅度：做 14 節開頭那個 A/B。若 0.2.0 明顯更快，那就是上游要修的問題，砍 bundle 只是止痛。
  3. 不要做（目標機已證偽）：加防毒排除、把 %APPDATA%\npm 搬到別的磁碟、改電源計畫、開 NODE_COMPILE_CACHE。理由都一樣：比值 >100%，行程沒有在等。
