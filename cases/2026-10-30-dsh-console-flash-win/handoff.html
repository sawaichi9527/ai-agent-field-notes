覆核：dsh web 經外掛重啟後的「DOS 閃一下」— 原始假設不成立

本文件原先記錄「閃爍＝open 缺 windowsHide」的因果鏈。2026-10-30 於目標機完成實測後，該假設被否證：鏈條上兩個 spawn 都不會產生 console。本文保留原假設的分析，但把結論、責任歸屬與 issue 草稿全部作廢。

關於 open 與 dsh-web-app：不要回報，它們無罪

在已驗證可建立 console、且無檔案沙箱的環境下，逐 hop 實測 has=False visible=False attached=0——包含「完全不帶 windowsHide」的對照組。也就是說，在這條鏈上缺 windowsHide 不會導致閃爍；決定 console 是否成立的是子行程有沒有拿到有效的 stdio 控制代碼，而這條鏈每個 hop 都把 stdio 重導或忽略了。

因此：第 10 節那兩份針對 open／dsh-power-xc 的 issue 草稿請勿送出；第 9 節的責任歸屬作廢。但要回報的對象換人了——見第 13、14 節。

最終結論：真因是 @goodandready/dsh-gitea 每 4 秒 spawn git 時缺少 windowsHide 已修復並驗證

2026-10-30 20:30：在 git-local.js 的兩處 exec() 選項補上 windowsHide: true 後，連續重開三次都沒有再閃。

完整因果鏈、證據與修法見 第 13 節；可直接送出的 issue 草稿見 第 14 節。

本文前半（第 3–10 節）記錄的是被否證的假設：open／dsh-web-app 的 browser handoff 鏈確實不會產生 console（四組實驗＋對照組可證）。真正的元凶在完全不同的地方。

外掛由 0.7.39 升到 0.7.41，lib/git-local.js 被整檔替換，兩處 windowsHide 消失，症狀原樣回來（正是第 13.4 節預告的失敗模式）。

1. 覆核後的結論

四句話

  1. 重啟後的新實例沒有主控台——這點成立（MainWindowHandle=0、全機 conhost=0），但它是 detached 重啟的預期結果，不是 bug。
  2. 「黑窗一閃＝PowerShell 被分配新 console」不成立。兩個 hop 實測都沒有 console：hop1（web-app 的 node --eval 啟動器）與 hop2（open 的 powershell）皆為 has=False。
  3. 決定 console 的不是 windowsHide，是 stdio。只要子行程的 stdio 是 NUL 或檔案（stdio:'ignore'、重導），Windows 就不會分配 console。兩層都已這樣做，所以閃不出來。
  4. 要回報，但對象不是 open。--no-open 只能少開分頁；真正的元凶是 @goodandready/dsh-gitea 每 4 秒 spawn git 缺少 windowsHide（已修復並驗證，見 第 13 節）。

3. 原始假設：閃爍的因果鏈 已否證

以下鏈條的程式碼描述全部正確（逐行核對過），但第 ④ 步的結論（會產生可見黑窗）是錯的。保留是為了說明錯在哪裡。
① 使用者在 GUI 按重啟 → dsh-power-xc 產生 detached helper，等舊行程結束、等 3080 釋放、等 session 檔落地。屬實
② helper 以 detached:true, windowsHide:true, stdio:['ignore', out, out] 重啟 node bin.js web → 新實例沒有主控台。屬實
③ 新實例沿用原始 argv（argc=3，沒有 --no-open）→ openBrowser 為 true → 執行 browser handoff。屬實
④ handoff 先 spawn node --eval，再由 open spawn powershell.exe；open 沒設 windowsHide → Windows 為 PowerShell 配置新 console → 黑窗一閃。 否證 這一步不會生 console。

5. 為什麼這個假設看起來很合理（但錯在哪）

錯在一個流傳很廣、但被過度簡化的說法：

「沒有主控台的行程啟動另一個 console 程式時，Windows 會為它配置新主控台，除非帶 CREATE_NO_WINDOW（windowsHide:true）。」

實際規則是：子行程會不會拿到 console，取決於建立時有沒有給它有效的 stdio 控制代碼。

  • 呼叫端明確指定 stdio（'ignore' → NUL、或檔案／管線控制代碼）時，Windows 不會再配一個 console。這條鏈的兩個 hop 都屬此類 → 不會閃。
  • 只有在 stdio 未指定、必須把子行程接到「不存在的 console」時，才會發生「配一個新的給你」的情形。
  • windowsHide（CREATE_NO_WINDOW）是額外的保險，不是這個情境下的決定因素。

換句話說：dsh-web-app 的 stdio: 'ignore' 與 open 的 childProcessOptions.stdio = 'ignore' 已經把閃爍擋掉了，只是擋的方式不是靠 windowsHide。

7. 還能做什麼

方案 A：--no-open（唯一有實質好處的選項）

dsh web --no-open

因為 dsh-power-xc 重啟時沿用原始 argv（relaunch = [execPath, ...execArgv, ...argv.slice(1)]，且全檔 0 處提到 --no-open），這個旗標會被重啟流程保留：之後每次外掛重啟都不會再開新分頁，也少一次無謂的 spawn。

但理由已經不是「消除閃爍」——閃爍本來就不存在。純粹是「不想每次重啟多一個分頁」。

方案 B：保有主控台的重啟方式

在 Windows Terminal 裡跑 dsh web，要重啟就在同一視窗 Ctrl+C 再重下。這解決「認不出實例」與「看不到網址」兩個問題，與閃爍無關。

方案 C：維持現狀（外掛關閉 → DOS 重開）

只要知道：任何還開著的舊 DOS 視窗都停不掉新實例，停它要用 PID 或外掛。

不要去改 node_modules/open/index.js 補 windowsHide。不只是「升級會被覆蓋」——更根本的是改了也沒有用，這個情境本來就不會生 console。改了只會讓你之後回報問題時難以重現。

8. 怎麼判斷現在跑的是哪個實例

# 1) 誰在聽 3080
netstat -ano | Select-String ':3080\s+0.0.0.0:0\s+LISTENING'

# 2) 這個 PID 有沒有主控台（0 = 沒有，這是預期）
Get-Process -Id <PID> | Select-Object Id, ProcessName, MainWindowHandle, StartTime

# 3) 它是「外掛重啟」還是「使用者自己啟動」
Get-Content "$env:USERPROFILE\.dsh\restart-helper-<PID>.log"
restart-helper-<PID>.log 內容代表
只有 loaded pid=…不是 helper 重啟的（但仍可能是無 console 啟動）
有 spawned pid <PID> (attempt 1)由外掛 helper 重啟的，無主控台、輸出在 dsh-web.log
修正：原版本寫「只有 loaded → 有主控台」，這是錯的。loaded 只代表該行程載入了 helper 模組，與有沒有 console 無關——本機 22156 就是只有 loaded 卻 MainWindowHandle=0。要判斷有沒有 console 只能看 MainWindowHandle。

11. 若你仍然看到閃爍：怎麼往下查 已解答

本節已由第 12 節解答。原本列的四個候選中，第 1 個（舊視窗關閉）與第 3 個（瀏覽器／其他程式自己的視窗）方向正確；真正的來源是一個與 dsh 完全無關的常駐程式。以下保留推論方法，供日後遇到類似現象時參考。

結論是「這條鏈不閃」。若你實際重啟時仍然看到黑窗，來源不在這裡。依可能性排序：

  1. 舊視窗關閉的視覺殘留：原本是在 DOS／Windows Terminal 視窗裡啟動的，重啟時那個視窗關掉——看起來像「閃一下」。用 restart-helper-*.log 確認該實例是否真是 helper 重啟；若是，原本的視窗本來就會消失。
  2. 其他外掛自己 spawn 了行程：在閃爍的瞬間抓新行程（見下方驗收方式），看看到底是誰被啟動。
  3. 瀏覽器端：某些預設瀏覽器冷啟動時會先出現一個短命的主控台／啟動器視窗。
  4. Windows 11 的差異：Windows Terminal 接管 console 的行為不同，反過來也可能在 Win10 出現 Win11 沒有的視覺效果。
驗收方式（給未來的自己）：閃爍與否不能用「感覺」驗收。要在閃的瞬間記錄「新增了哪個行程、它的 MainWindowHandle 是多少」，否則會再次掉進「合理但錯」的假設。

12.1 為什麼會誤以為是 dsh 造成的

  1. 按重啟後，原本跑 dsh web 的那個 DOS 視窗結束、回到提示字元——桌面上少了一個佔住前景的視窗，這些 popup 才變得顯眼。
  2. NVIDIA Sync 的輪詢重啟前就在跑，節奏完全沒變（下表的時間軸可證）。
  3. 「瀏覽器輸入被打斷」是 console 視窗搶焦點的典型症狀，只在你開始用瀏覽器之後才有感——也就是重啟之後。

  1. （建議，可逆）工作管理員 → 啟動 → 停用「NVIDIA Sync」，然後從系統匣右鍵退出。下次登入就不會再起來，也不會再閃。
  2. 用完再開：需要時手動執行 C:\Users\\AppData\Local\Programs\nvidia-sync\NVIDIA Sync.exe。
  3. 檢查它自己的設定有沒有輪詢間隔：若有，拉長到 60 秒以上即可大幅減少干擾。

先確認自動啟動來源（單行指令）：

Get-CimInstance Win32_StartupCommand | Where-Object { $_.Command -match 'nvidia' } | Format-List Name,Command,Location
dsh 這邊不需要改任何東西。--no-open、dsh-power-xc、open、dsh-web-app 全都與此事無關。先前「缺 windowsHide」的假設與對應的 issue 草稿可以永久作廢。

13. 真因（已修復並驗證）：dsh-gitea 每 4 秒 spawn git 缺 windowsHide 確認

13.1 完整因果鏈

① 瀏覽器裡的 GUI 載入 dsh-gitea 的狀態元件，它每 4 秒輪詢一次：lib/client.js:1905／:1918 的 setInterval(fetchStatus, 4000)。這個間隔是寫死的，沒有設定項可調。
② 請求打到 /git-status，路由處理器呼叫 isGitDir(dir, execFile)（lib/routes.js:246 與 :294）。
③ isGitDir() 執行 readGit(execFile, cwd, ['rev-parse', '--show-toplevel'])（lib/git-local.js:64）。
④ readGit() 用 exec('git', args, { cwd, timeout: 20_000, maxBuffer })（lib/git-local.js:39）——沒有 windowsHide。整個套件裡 windowsHide 只出現在 plugin-updater.js:192，與這條路徑無關。
⑤ git.exe 產生 console 視窗（部分時刻 visible=True）→ 短暫可見且搶走前景焦點 → 你在瀏覽器打字會漏字。

13.2 證據

項目實測值
節奏3.96 / 4.32 / 3.68 / 4.03 / 4.01 / 4.04 / 3.98 / 3.98 / 4.08 秒
擁有 console 的行程git.exe，父行程 = node.exe（PID 22668，即 bin.js web）
命令列git rev-parse --show-toplevel
可見性7 次觀測中 4 次 visible=True、3 次 False
修復後補上 windowsHide: true → 連續重開三次都不再閃

13.3 為什麼這麼難抓

  1. 擁有 console 的行程活不到幾十毫秒：用 Get-Process 輪詢（40ms 一次）幾乎必然漏掉；而且這台舊 CPU 上一次 Get-Process 就要上百毫秒，實際輪詢遠慢於設定值。最後是靠「列舉視窗」再反查 PID 才抓到（視窗存在時，擁有它的行程一定還活著）。
  2. 環境裡有兩個獨立輪詢者：NVIDIA Sync 每 5.2 秒、dsh-gitea 每 4.0 秒。停掉前者後節奏變成 4.0 秒，看起來像「問題還在、但換了節奏」——這正是把兩者分開的關鍵線索（第 12 節）。
  3. 時間相關性會騙人：重啟後瀏覽器才開 GUI，GUI 一開才開始輪詢——所以現象「只在重啟後出現」，但真正的原因跟重啟本身無關，是「重啟導致瀏覽器開起來」。

13.4 修法

在 lib/git-local.js 的兩個 exec 選項各補一個 windowsHide: true（readGit L39 的 20_000、writeGit L55 的 30_000）：

// 修法前
await exec('git', args, { cwd, timeout: 20_000, maxBuffer: 2 * 1024 * 1024 })

// 修法後
await exec('git', args, { cwd, timeout: 20_000, maxBuffer: 2 * 1024 * 1024, windowsHide: true })
這是直接改 node_modules，外掛更新後會被覆蓋——2026-11-09 升級到 0.7.41 時已實際發生（見上方覆核框）。所以正解仍是回報上游（草稿見第 14 節），本地補丁只當臨時措施；重套請用 reapply-windowsHide-patch.ps1（冪等、自動備份）。

14. 可送出的 issue 草稿（@goodandready/dsh-gitea）新

Title: Windows: the 4-second status poll flashes a console window and steals foreground focus

## Environment
- Windows 10 Enterprise LTSC 2019 (17763.9376), Node v24.21.0
- @deepseek-ai/dsh 0.2.1-rc.5
- @goodandready/dsh-gitea 0.7.39 (also reproduced on 0.7.41, 2026-11-09)

## Steps
1. Start `dsh web` and open the GUI in a browser (so the status chip starts polling).
2. Leave it idle; watch the desktop.

## Actual
- A console window appears and disappears roughly every 4 seconds.
- It steals foreground focus: typing in the browser loses characters.
- The window is owned by `git.exe`; its parent is the dsh node process (PID of `bin.js web`),
  and its command line is `git rev-parse --show-toplevel`.

## Expected
The git probe should be invisible; no console window, no focus change.

## Root cause
The status component polls every 4000 ms (`lib/client.js:1905` and `:1918`,
`setInterval(fetchStatus, 4000)` — the interval is hard-coded, no setting exposes it).
Each poll hits `/git-status`, whose handler calls `isGitDir()` (`lib/routes.js:246`, `:294`),
which calls `readGit(execFile, cwd, ['rev-parse', '--show-toplevel'])` (`lib/git-local.js:64`).
`readGit()` then runs:

    exec('git', args, { cwd, timeout: 20_000, maxBuffer: 2 * 1024 * 1024 })

without `windowsHide`. The string `windowsHide` does not appear anywhere in
`git-local.js`; the only occurrence in the package is `plugin-updater.js:192`.
When the dsh process has no console (the normal case after a plugin restart),
the spawned `git.exe` can receive a fresh console window.

## Fix
Add `windowsHide: true` to the exec options in `readGit()` (L39) and `writeGit()` (L55).

## Verification
With `windowsHide: true` applied locally, three consecutive `dsh web` restarts produced
no console window and no focus loss. Reverting the two-line change reproduces the flash
every ~4 seconds.

另可順帶建議：把 4000 ms 這個間隔做成設定項（或改事件驅動），可以一併降低無謂的 git 呼叫。
